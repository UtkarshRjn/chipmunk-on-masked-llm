01 — The Problem

Why standard KV-Cache cannot work in DLMs

In autoregressive LMs (GPT, LLaMA etc.), KV-cache is the core speedup: compute K,V for each token once, cache them, reuse forever. This makes each new token O(1) instead of O(L). But diffusion language models break both assumptions KV-cache relies on.

AR LM — KV-cache works ✓

Causal (left-to-right) attention

Token i only attends to tokens 1..i. Once token i is generated, K[i] and V[i] never change — nothing to the right can affect them.

Fixed sequential order

Always generates left → right. Next position is always known in advance.

DLM — KV-cache breaks ✗

Bidirectional attention

Every token attends to every other token. When ANY token unmasks, the K,V of ALL other tokens can shift. K[i] at step t ≠ K[i] at step t+1.

Non-sequential decoding order

Any masked position can be chosen next based on confidence. Next position is unknown until the forward pass completes.

The complexity cost of no cache

AR with KV-cache: O(L²) total — O(L) per step × L steps DLM without cache: O(L³) total — O(L²) per step × L steps For L = 512, T = 512: AR: 512² = 262k operations per step DLM: 512² × 512 = 134M total → DLMs are ~512× more expensive

02 — Key Observation

Representation Dynamics: what actually changes

The paper investigates whether K and V can be reused despite bidirectional attention. They measure how much K and V change between consecutive denoising steps for each token.

Three findings from Figure 2

Finding 1 — K,V are highly similar across steps

Despite step-to-step differences, K and V embeddings show consistently high cosine similarity across timesteps (pairwise similarity heatmap shows values above 0.975 for most step pairs). They change, but not dramatically.

The representations are NOT completely different each step. They drift slowly — which is what makes caching feasible at all.

Finding 3 — Largest change happens AT the decoding step

For each token, the step where it transitions from [MASK] → decoded is the step with the maximum K,V change. Before that step: fluctuating. After that step: stable.

||dK/dt|| is maximum at the exact step token transitions MASK → decoded Before decode: K,V change a lot each step At decode: K,V change MOST (biggest jump) After decode: K,V barely change ← safe to cache
This is the empirical foundation everything builds on. If you cache K,V immediately at the decoding step, you capture a bad (maximally-changing) value. Wait one more step → K,V has settled → safe to cache. This motivates the ONE-STEP DELAY.
03 — dKV-Cache-Decode

Delayed Caching — near-lossless variant

The core idea: only cache K,V for tokens that have been decoded. But with a one-step delay — wait one extra step after decoding before caching, because the decoding step itself has the largest K,V change.

The caching rule

At step t: Mt = set of currently MASKED tokens Mt-1 = set of masked tokens from PREVIOUS step I \ Mt = all decoded tokens I \ Mt-1 = decoded tokens from previous step (one-step delayed) CACHE: K,V for tokens in I \ Mt-1 (decoded last step, now stable) COMPUTE: K,V for tokens in Mt-1 (still masked last step, may change) Attention formula: z_t = softmax( Q^{Mt-1}_t @ K^I_t^T ) @ V^I_t where K^I_t = concat_reorder( K^{I\Mt-1}_{t-1}, K^{Mt-1}_t ) ↑ from cache ↑ freshly computed

Cache Refreshing

Even decoded tokens can slowly drift if the sequence context keeps changing around them. Without refreshing, error accumulates over many steps.

Every N steps, discard all cached K,V and recompute everything from scratch. This resets any accumulated drift to zero. Typical setting: refresh every 4–8 steps.

Analogy: like Chipmunk's dense anchor step. Every N steps = full recompute to reset error. Between refreshes = use cached values.

Pseudocode

def dkv_cache_decode_step(x, t, Mt, Mt_prev, K_cache, V_cache, refresh_every=8):
    # Mt      = masked tokens at step t
    # Mt_prev = masked tokens at step t-1 (one-step delay)

    if t % refresh_every == 0:
        # Full refresh — recompute everything
        Q, K, V = compute_qkv(x, all_positions)
        K_cache = K[I \ Mt]   # cache decoded tokens
        V_cache = V[I \ Mt]
    else:
        # Sparse step — only compute for masked tokens
        Q_masked = compute_q(x, Mt_prev)    # Q only for still-masked
        K_new, V_new = compute_kv(x, Mt_prev)  # K,V for masked (may change)

        # Full K,V = cached (decoded tokens) + fresh (masked tokens)
        K_full = concat_reorder(K_cache, K_new)
        V_full = concat_reorder(V_cache, V_new)

        # Attention: masked queries attend to ALL keys
        output = attention(Q_masked, K_full, V_full)

        # Update cache with newly-stable tokens (one-step delayed)
        newly_stable = Mt_prev \ Mt   # tokens decoded THIS step
        K_cache[newly_stable] = K_new[newly_stable]
        V_cache[newly_stable] = V_new[newly_stable]

    return output, K_cache, V_cache
04 — dKV-Cache-Greedy

Aggressive Caching — reduces O(L³) to O(L²)

dKV-Cache-Decode still has O(L³) complexity because the set of masked tokens |Mt| starts at L and only shrinks by ~1 each step — you still compute Q for nearly all tokens at early steps.

dKV-Cache-Greedy fixes this by making |Mt| a fixed small size at every step, regardless of where we are in the denoising process.

What Mt contains in Greedy mode

Mt = { Dt } the token being decoded at THIS step ∪ { D(t-1) } the token decoded LAST step (one-step delay rule) ∪ { W(t) } a local window of neighbors around Dt (size ≤ 6) |Mt| = 1 + 1 + w = small constant (e.g., w=4 → |Mt| = 6) → per-step cost: O(|Mt| × L) ≈ O(6L) = O(L) → total: O(L × L) = O(L²) ← same as AR!

Why include Dt

The token being decoded right now has the largest K,V change — it just transitioned from MASK. Must be in the active set.

Why include W(t)

Tokens neighboring the current decode position are likely attending to it heavily. Including a small window dramatically improves accuracy with minimal extra cost.

Complexity comparison

MethodPer-step costTotal complexityQuality
Full DLM (no cache)O(L²)O(L³)Perfect
dKV-Cache-DecodeO(|Mt| × L) decreasingO(L³) but faster constantNear-lossless
dKV-Cache-GreedyO(|Mt| × L) fixed smallO(L²)Some degradation

Trade-off: Greedy achieves the same complexity as AR (O(L²)) but at the cost of some accuracy, because many decoded tokens get stale K,V between refreshes. The window size and refresh interval control this tradeoff.
05 — The One-Step Delay

Why the delay is critical — not optional

This is the single most important design decision. Without the one-step delay, the method fails catastrophically at high cache ratios.

Without delay — cache immediately

At step t, token X decodes. Immediately cache K[X], V[X] from step t and reuse forever.

Problem: step t is the maximum change step for token X. K[X] at step t is very different from K[X] at step t+1 (which is the stable value). Caching the unstable value poisons the cache.

Result from Figure 3: performance collapses to near-zero accuracy as cache ratio increases. The stale K,V values actively mislead attention.

With one-step delay — cache next step

At step t, token X decodes. Do NOT cache yet. At step t+1, K[X] has settled to its stable value. Now cache K[X] from step t+1.

The one-step delay lets the representation land at its stable value before we lock it in the cache.

Result from Figure 3: performance stays near-perfect even at high cache ratios. The delay makes the cache content reliable.

What "one-step delay" means in the algorithm

Normal caching (no delay): At step t: X just decoded → cache K[X]_t immediately One-step delayed caching: At step t: X just decoded → don't cache yet, still compute K[X] At step t+1: X is now in I\Mt-1 → NOW cache K[X]_{t+1} The index set for what's cacheable at step t: No delay: I \ Mt (everything decoded BY step t) One-step: I \ Mt-1 (everything decoded BY step t-1) Difference: the tokens decoded at exactly step t are excluded from the cache for one more step.
In code: instead of checking if token in decoded_this_step, you check if token in decoded_last_step. One line change. Massive impact on accuracy.
06 — concat_reorder

How it's implemented efficiently

The algorithm needs to: (1) gather cached K,V from arbitrary positions, (2) concatenate with fresh K,V, (3) run attention, (4) scatter results back to original positions. Doing this naively with random indexing is slow.

The naive problem

AR KV-cache just appends: [K_cached ; K_new] — simple contiguous memory, fast.

dKV-Cache needs to gather scattered positions: decoded tokens are at positions [2,4,5,7...] in the original sequence — not contiguous. Gathering these requires indexing, which generates non-contiguous memory accesses → slow.

Additionally, after attention, results must be scattered back to original positions. Two expensive indexing operations per step.

The concat_reorder solution

Key idea: reorder the token sequence at the START of each forward pass so that cached tokens (decoded, I\Mt-1) are on the LEFT and uncached tokens (masked, Mt-1) are on the RIGHT. This makes concatenation contiguous.

Example: 8 tokens, decoded at t-1: {2, 4, 5} Original order: [0, 1, 2, 3, 4, 5, 6, 7] Reordered: [2, 4, 5 | 0, 1, 3, 6, 7] ↑cached ↑uncached (masked) Now: K_cached is contiguous at left of K matrix K_fresh is contiguous at right of K matrix concat = just K matrix as-is, no gather needed! At next step, if token 7 also decodes: Reorder: [2, 4, 5, 7 | 0, 1, 3, 6] → just move token 7 from right to left side

Positional embeddings (RoPE) are also reordered — this is cheap since it happens once per layer, shared across all heads.

The reorder operation

# At each step, compute a permutation index to reorder tokens
# Cached tokens (decoded) go left, uncached (masked) go right

def concat_reorder(K_cached, K_fresh, decoded_positions, masked_positions):
    # Reorder positional embeddings once
    PE_reordered = PE[decoded_positions + masked_positions]

    # After computing Q,K,V for the reordered sequence:
    # K matrix is already [K_decoded | K_masked] — just concatenate
    K_full = concat(K_cached, K_fresh)   # contiguous — fast

    # For next step: compute new reorder mapping
    # (adds any newly decoded tokens to the left side)
    new_decoded = decoded_positions + newly_decoded_this_step
    new_masked  = masked_positions - newly_decoded_this_step
    reorder_idx = compute_permutation(new_decoded, new_masked)

    # Reorder K,V for caching at next step
    K_cache_next = K_full[reorder_idx[:len(new_decoded)]]
    return K_full, K_cache_next
This is the operator dKV-Cache authors say has "substantial potential for further optimization" — specifically, this is what Chipmunk's cp.async gather kernel would replace for the hardware-accelerated version.

Key analytical findings

More steps → bigger gain

As the number of denoising steps T increases, dKV-Cache's advantage over the baseline grows. At T=512, GSM8K improves from 80.97% → 83.13% accuracy while being faster. More steps = more opportunities for cache reuse.

Batch size matters for speed

At batch size 1, dKV-Cache can actually be SLOWER than baseline because gather/scatter operations generate non-contiguous memory accesses that are inefficient. Larger batch sizes (8+) deliver the full speedup reliably.

09 — Limitation and the Research Gap

What dKV-Cache explicitly leaves open

Verbatim from §5 Conclusions

"One primary limitation of this work lies in its focus on algorithmic design in isolation. While our proposed method introduces an effective caching mechanism from a purely algorithmic perspective, diffusion language models also exhibit substantial room for improvement at the system level. We believe that future research integrating algorithmic innovations with system-level optimization, such as memory management, parallelism, and hardware-aware execution, could unlock further efficiency gains and performance improvements for DLMs."

What this means concretely

What dKV-Cache did NOT do

  • Tested on A6000 and H20 — not H100/Hopper
  • No cp.async scattered gather from HBM
  • No wgmma tensor-core optimization
  • No warp specialization for cache I/O
  • concat_reorder is PyTorch-level — not kernel-level
  • No formal error bound on approximation quality
  • Selection criterion: recency (decode order), not magnitude

What the research proposal adds

  • Hopper-native kernel: cp.async + TMA + wgmma
  • Magnitude-based active set (Chipmunk's approach)
  • Warp specialization for cache reads/writes
  • Formal error bound (first in MDM literature)
  • H100 characterization (nobody has done this)
  • Composition with FastDLLM + speculative decoding

How dKV-Cache and Chipmunk relate to the proposal

Summary: dKV-Cache proves empirically that K,V can be reused in diffusion language models and gives the algorithmic framework for how to do it. The research proposal takes that framework and asks: what if we also added Chipmunk's kernel-level machinery (cp.async gather, wgmma, warp specialization) AND replaced recency-based selection with magnitude-based selection? That's the missing piece dKV-Cache's authors explicitly called for.
