01 — The Two Problems

Why LLaDA is slow: two separate bottlenecks

Fast-dLLM identifies and attacks two independent sources of slowness in masked diffusion inference. They compound — fixing both gives multiplicative speedup.

Problem 1: No KV Cache

Standard KV cache works for autoregressive (causal) models. In LLaDA, bidirectional attention means every denoising step must recompute all K, V for all tokens from scratch.

Each step: full O(L²) attention L=1024 tokens, T=1024 steps: → 1024 × O(L²) total work → No reuse between steps Autoregressive equivalent: → O(L) per new token with KV cache → 1000× less computation
Fix: approximate KV cache — reuse K,V from previous steps within a "block" of decoding. Cache is valid because K,V change very little step to step.

Problem 2: Parallel Decoding Quality

To reduce the number of steps, you need to unmask multiple tokens per step (τ-leaping). But the model predicts each token independently, breaking dependencies between tokens that should be correlated.

Task: "list two words that go together: [M] [M]" Model predicts independently: p("full" | context) = 0.4 p("house" | context) = 0.3 (but needs "full" first!) p("high" | context) = 0.35 Sampled: "full" at position A, "high" at position B Result: "full high" — incoherent! Correct: "full house" or "high card"
Fix: confidence-aware decoding — only unmask tokens whose confidence is very high. High confidence = the correct token is clear regardless of what neighbors are doing.
The two fixes are orthogonal: KV cache reduces per-step cost, parallel decoding reduces number of steps. Stacking both gives multiplicative speedup: 3× (cache) × 2.5× (parallel) = 8×, matching the measured 8.1× for GSM8K at length 256.
02 — The Key Observation

KV activations barely change between adjacent steps

The entire Fast-dLLM caching approach rests on one empirical observation: within a decoding block, K and V values are nearly identical between consecutive steps.

Why are K, V so similar between adjacent steps?

K_i = x_i · W_K (key for token i) V_i = x_i · W_V (value for token i) Between step t and step t-1: - Tokens that were ALREADY unmasked: x_i unchanged → K_i, V_i unchanged - Tokens that were JUST unmasked this step: x_i changed (mask → real token) If only 1–2% of tokens change per step (small τ-leap): → 98–99% of K, V vectors are IDENTICAL between steps → The remaining 1–2% change — causing the low average sim Net cosine similarity: 0.95–0.99 (very high) ✓ The paper verifies this for BOTH prompt tokens (Figure 3a) and suffix/masked tokens (Figure 3b) — both show high similarity.
Why this matters: If K, V at step t is 0.97 similar to K, V at step t-1, then the attention output using the cached K, V is very close to the true attention output. The approximation error is tiny and the accuracy impact is negligible.
03 — Block-wise KV Cache

Block-wise KV Cache: PrefixCache and DualCache

Fast-dLLM's cache works differently from autoregressive KV cache. Rather than caching per-token, it caches per-block across denoising steps.

The block-wise decoding scheme

The response is split into K blocks of size B tokens each. Blocks are decoded one at a time — only the current block is being actively unmasked.

Sequence layout (prompt + 3 blocks, B=32 tokens each):
Prompt (fixed)
Block 0
(done)
Block 1
(active)
Block 2
[M][M]...[M]
■ Prompt — never changes, cache computed once
■ Block 0 — fully decoded, K,V cached
■ Block 1 — currently being decoded (T steps of unmasking)
■ Block 2 — still fully masked, K,V for [MASK] tokens cached

PrefixCache — caching the prompt

The simplest version: compute K, V for the prompt once, cache them, and reuse across all T decoding steps within Block 1.

Without cache (per step): Compute K,V for: prompt(P tokens) + block1(B tokens) + rest(M tokens) Cost: O((P + B + M)²) PrefixCache (per step within block 1): Prompt K,V: loaded from cache (free) Block 1 tokens: recompute K,V (these change as tokens unmask) Rest (still masked): K,V can also be cached if not changing Cost reduction: O(B²) instead of O((P+B+M)²) P = 256 tokens prompt, B = 32, M = remaining blocks Speedup: up to 3× for typical lengths
The cache update happens after the full block is done — not within the block. So within the block, the approximation is: "pretend previously-decoded tokens' K,V haven't changed." They change by <5% — negligible impact on accuracy.

DualCache — also caching the suffix

DualCache extends caching to the suffix (blocks not yet decoded). When decoding Block 1, the suffix (Blocks 2, 3, ...) are still all [MASK]. Their K, V can also be cached — the [MASK] embedding doesn't change until those blocks start decoding.

DualCache: cache prompt K,V AND suffix K,V Cached tokens during Block 1 decoding: [Prompt K,V] [Block 0 K,V] [active Block 1] [suffix K,V cached] Only Block 1's current tokens are recomputed each step. DualCache speedup vs PrefixCache: Long sequences (gen=1024): 27.6× vs 18.6× (DualCache wins more) Short sequences (gen=256): 9.4× vs 10.0× (PrefixCache slightly better) Why DualCache wins at long gen: More suffix tokens → more compute saved by caching them

The approximation cost: when does it hurt?

B=32 is the sweet spot. Within a block of 32 steps, unmasking ~1 token/step means only 32 tokens change — the rest of the L tokens' K,V are nearly identical. After 32 steps you refresh.

04 — Confidence-Aware Parallel Decoding

Confidence-Aware Parallel Decoding

The second bottleneck: unmasking tokens one at a time requires too many steps. Unmasking many at once causes incoherent combinations. The fix: only unmask tokens you're very confident about.

The intuition

Example: "The capital of France is [M]." Model predicts: p("Paris" | context) = 0.97 ← very confident p("city" | context) = 0.02 p("the" | context) = 0.01 Threshold τ = 0.90: 0.97 > 0.90 → unmask this token → "Paris" ✓ Safe to decode independently because: Even without seeing neighboring [M] tokens, the answer is unambiguously "Paris".
Contrast with a low-confidence case: "The [M] and [M] are best friends." Both tokens are interdependent — "Romeo" needs "Juliet". Confidence for each might be 0.4 individually. Below threshold → don't unmask yet, wait for more context.

Two variants

Threshold strategy

Set a global confidence threshold τ (e.g., 0.9). At each step, unmask all masked tokens with confidence ≥ τ. Always unmask at least one (highest confidence) to guarantee progress.

for each masked position i: c_i = max softmax(logits[i]) if c_i >= τ: unmask position i Always unmask: argmax(c_i) τ = 0.9 → avg 3.25 tokens/step τ = 0.7 → avg 7.0 tokens/step

Simple, easy to tune. τ=0.9 gives best accuracy-speed tradeoff.

Factor strategy (theoretically grounded)

Instead of a fixed threshold, dynamically choose n tokens to decode such that (n+1)·(1-confidence_n) < f, where f is a factor hyperparameter.

Sort confidences: c_(1) ≥ c_(2) ≥ ... ≥ c_(m) Find largest n such that: (n+1) · (1 - c_(n)) < f Unmask top-n tokens. f = 1.3 → avg ~3.8 tokens/step f = 1.9 → avg ~5.7 tokens/step

Tied to Theorem 1 formally. Typically 40-50% higher throughput than threshold at 1-3% accuracy cost.

Parallel token count across decoding steps

Parallel tokens per step at threshold τ=0.9 (from Figure 7): Steps 1–20 (high noise): ~2–4 tokens/step (most tokens still [MASK], hard to be confident) Steps 20–60 (mid-decoding): ~4–8 tokens/step ← peak parallelism (enough context for high-confidence predictions) Steps 60–100 (near done): ~2–5 tokens/step (few masked tokens left, high variance) Average across all steps: ~3.25 tokens/step → Reduces T from 1024 to ~315 steps for same response length
05 — The Formal Guarantee

Theorem 1: When parallel decoding = sequential decoding

The paper proves that under high confidence, decoding tokens independently (parallel) gives the same result as decoding them sequentially (accounting for dependencies).

Theorem 1 (informal)

Suppose you are decoding n tokens simultaneously, and each token's correct prediction has marginal probability > 1-ε. If (n+1)·ε ≤ 1, then:

argmax p(x_1,...,x_n | context) [true joint] = argmax q(x_1,...,x_n | context) [product of marginals] i.e., greedy parallel decoding = greedy sequential decoding.

The condition (n+1)ε ≤ 1 means: the more tokens you decode in parallel, the more confident each one needs to be. Decode 9 tokens simultaneously → each needs confidence > 90%.

Interpreting the condition

n tokens decoded simultaneously, each with confidence > 1-ε: n=1 (sequential): any ε < 1 works → no confidence requirement n=4 tokens: need ε < 1/5 = 0.20 → confidence > 80% n=9 tokens: need ε < 1/10 = 0.10 → confidence > 90% ← threshold τ=0.9 n=19 tokens: need ε < 1/20 = 0.05 → confidence > 95% At τ=0.9: safely decode up to 9 tokens in parallel. In practice decoder averages 3.25 tokens/step (well within the guarantee).
Why this is not obvious: You might think "I need to account for dependencies, so I can't decode independently." The theorem says: when each token is individually confident, dependencies become irrelevant — the most likely joint outcome IS the product of most-likely marginals. High confidence kills ambiguity.

The poker hand example revisited

Bad case (low confidence): "poker hands: [M] [M]" p("full") = 0.35, p("house") = 0.30 — below threshold → Don't decode yet, keep masked, get more context Good case (high confidence): "She lives in [M], the capital of France." p("Paris") = 0.97 — above threshold → Safe to decode: "Paris" independently, dependency doesn't matter The threshold exactly controls this tradeoff: Only decode when you're sure enough that dependencies don't matter.
06 — Full Algorithm

Fast-dLLM: Full Algorithm

Combining block-wise KV cache with confidence-aware parallel decoding into one coherent inference loop.

def fast_dllm_generate(model, prompt, response_len,
                       B=32, τ=0.9, use_dual_cache=True):
    L = len(prompt) + response_len
    x = prompt + [[MASK]] * response_len

    # ── CACHE INIT ─────────────────────────────────────────────
    # Compute KV cache for prompt (and suffix if DualCache)
    kv_cache = model.compute_kv(x, positions=prompt_positions)
    if use_dual_cache:
        kv_cache += model.compute_kv(x, positions=suffix_positions)
    # ── BLOCK-WISE DECODING ─────────────────────────────────────
    for block_k in range(num_blocks):
        s = prompt_len + block_k * B
        e = s + B                       # [s, e) = current block

        # Inner loop: decode this block over T steps
        for step in range(T):
            # CACHE REUSE: prompt + decoded blocks + suffix from cache
            # Only compute attention for current block [s,e)
            logits = model.forward_with_cache(
                x[s:e],                 # current block only (fresh)
                kv_cache,               # everything else (cached)
            )                           # shape: [B, vocab_size]

            # CONFIDENCE SCORING
            confidence = softmax(logits).max(dim=-1)  # [B]

            # PARALLEL DECODING: unmask above-threshold tokens
            unmask_mask = (confidence >= τ) & (x[s:e] == MASK)
            if unmask_mask.sum() == 0:   # safety: always unmask at least 1
                unmask_mask[confidence.argmax()] = True

            x[s:e][unmask_mask] = sample(logits[unmask_mask])

            if (x[s:e] != MASK).all():
                break                   # block fully decoded

        # ── CACHE UPDATE ─────────────────────────────────────────
        # Recompute KV for the now-decoded block, update cache
        kv_cache.update(block_k, model.compute_kv(x[s:e]))
        # Next block will see fresh KV for this block

    return x[len(prompt):]

What makes it approximate (and why that's OK)

Within block 1 decoding, step 5 uses: KV_prompt = computed at initialization (exact) KV_block0 = computed after block 0 finished (exact) KV_block1 = NOT recomputed — uses step 4's values (approximate) KV_block2 = computed at initialization when all [MASK] (approx) Error sources: Block 1 cache: tokens in block 1 unmasked during step 1..4 K,V changed when [MASK]→real token cosine similarity: ~0.97 (negligible error) Block 2 cache: still all [MASK] — no change whatsoever cosine similarity: ~1.00 (exact) → The approximation error is tiny and quality impact is <1%

Why HumanEval gets less benefit from caching (1.3× vs 3.2×)

HumanEval generates code (up to 256 tokens). The prompt is short (function signature), so PrefixCache saves less. Code tokens also have lower baseline throughput (30.5 tok/s vs 6.7 for GSM8K) — meaning the model is already running at near-peak compute.

GSM8K (memory-bound, short context): Baseline throughput: 6.7 tok/s — limited by memory I/O Cache eliminates most HBM reads → 3.2× speedup HumanEval (compute-bound, longer code): Baseline throughput: 30.5 tok/s — limited by attention FLOPs Cache reduces memory I/O, but attention compute still bottleneck → Only 1.3× speedup from cache → To accelerate compute-bound workloads, you need to reduce the FLOPs themselves — not just memory I/O. That's what the research proposal targets with sparse kernels.
This is the exact gap the research proposal fills. Chipmunk-style column-sparse attention reduces actual FLOPs (not just memory), targeting the compute-bound regime where Fast-dLLM falls short.

08 — Limitations & What Comes Next

Limitations and What the Research Proposal Adds

Fast-dLLM's honest limitations

  • Block-level granularity only. Caches entire blocks — not individual token-column vectors. Approximation is coarser than column-sparse (like Chipmunk).
  • Compute-bound tasks still limited. HumanEval only 3.7×. The attention FLOPs themselves are not reduced — only memory I/O.
  • Pure PyTorch, no custom kernels. All results on A100 without FlashAttention-level kernel optimization. Hardware throughput ceiling not reached.
  • No H100 evaluation. All benchmarks on A100. H100 with its faster memory bandwidth would shift the compute-vs-memory boundary further.
  • Block size is a hyperparameter. B=32 optimal for most; multimodal tasks needed B=96. Different models and tasks may need different tuning.

What the research proposal adds (Chipmunk → MDMs)

Fast-dLLM approach: Granularity: Block-level (B=32 tokens cached/updated together) Selection: Recency-based (recently-decoded blocks get refreshed) Hardware: PyTorch on A100, no custom kernels Attention: Full O(L²) per step (just reuses cached K,V from other blocks) Speedup gap: HumanEval only 3.7× — compute still bottleneck Research proposal approach (Chipmunk on MDMs): Granularity: Column-level (individual K/V vectors, finer than blocks) Selection: Magnitude-based (top-k by ||K_t - K_{t-1}||) Hardware: ThunderKittens on H100-SXM5, custom cp.async + wgmma Attention: Sparse O(N·k) where k = 5% of N (fewer actual FLOPs) Target: 1.3–2× over Fast-dLLM on compute-bound tasks

The proposal is not a replacement for Fast-dLLM's block-wise caching — it composes with it. Fast-dLLM handles step-level and block-level reuse; the proposal handles within-step sparse attention kernels. Stacking both is explicitly in the research plan.
